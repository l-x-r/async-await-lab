POSTGRESQL DESIGN NOTES

PostgreSQL 设计,只留精华。

我读完了 4 个热门 PostgreSQL 设计 Skill 的原文(supabase、wshobson、Neon、ECC),把它们反复一致、可直接照做的规则合并成这一页。每条规则都标明了是“该这样”还是“别这样”,并附可复制的 SQL。

01 /表设计铁律

几个 Skill 一致同意的部分
主键

用 bigint identity;UUID 只在需要时用

  • 单库默认 BIGINT GENERATED ALWAYS AS IDENTITY。
  • 需要分布式 / 对外不可猜的 ID 才用 UUID,并且用时间有序的 v7(PG18+ 有 uuidv7(),更早版本用 pg_uuidv7 扩展)。
  • 随机 UUID v4 做大表主键会让索引碎片化、插入分散。
  • 时序 / 日志 / 事件表常常不需要主键,可用 (时间, 设备) 之类的自然键。
范式

先到 3NF,有实测证据再反范式

  • 反范式只用于“连接成本已被证明是瓶颈”的读多场景。
  • 物化视图是更干净的反范式读模型:REFRESH MATERIALIZED VIEW CONCURRENTLY,需要有唯一索引。
  • 数组适合标签这类简单有序列表;多对多关系用中间表,别用数组。
命名

全小写 snake_case

不带引号的标识符会被折叠成小写。带引号的 "UserId" 之后永远要加引号,ORM、工具和 AI 都容易踩坑。ORM 默认生成驼峰时,改配置而不是迁就它。

外键

外键列必须手动建索引

Postgres 不会给外键列自动建索引。没有索引时,JOIN 和 ON DELETE CASCADE 都会全表扫描,删父行还会长时间持锁。同时要显式写 ON DELETE / ON UPDATE 行为;循环依赖用 DEFERRABLE INITIALLY DEFERRED。

类型选择:避免 → 改用

避免改用原因
timestamp / timetztimestamptz始终存带时区的时刻;不要给它指定精度
varchar(n) / char(n)text性能相同;需要长度限制时加 CHECK (length(col) <= n)
money / float 存金额numeric(p,s)精确十进制运算
serialgenerated always as identitySQL 标准写法
int 做 IDbigintint 在约 21 亿处溢出
用 varchar 存布尔 / 数字boolean NOT NULL / numeric占用更小,比较更快,杜绝脏值
realdouble precision除非存储极度紧张
jsonjsonb除非必须保留原始键顺序
枚举

ENUM 只给“小而稳定”的集合

星期、美国州这类可以。订单状态这类会演化的业务值,用 TEXT + CHECK 或查找表,改起来不痛。

JSONB

只放可选 / 半结构化属性

核心关系留在普通列里。给 JSONB 加 CHECK (jsonb_typeof(col) = 'object') 约束形状;常查的标量字段抽成生成列再建 B-tree。

约束

  • NOT NULL 能加就加,常用值配 DEFAULT。
  • CHECK 只检查当前行,且 NULL 会通过 → 要和 NOT NULL 搭配:price NUMERIC NOT NULL CHECK (price > 0)。
  • UNIQUE 默认允许多个 NULL;PG15+ 用 UNIQUE NULLS NOT DISTINCT 限制只能有一个。
  • EXCLUDE 防重叠(订房防重订):EXCLUDE USING gist (room_id WITH =, booking_period WITH &&)。

几个 Postgres 特有的坑

  • 字段超长 / 精度溢出会直接报错,不会静默截断(往 NUMERIC(2,0) 塞 999 会失败)。
  • identity / sequence 有空洞是正常的(回滚、崩溃、并发都会产生),不要去“修”。
  • 堆表没有聚簇主键;CLUSTER 只是一次性重排,后续插入不会维持。
  • MVCC:更新和删除会留下死元组,靠 vacuum 回收;设计时避免“宽行被频繁更新”。
  • 大于约 2KB 的值会自动进 TOAST 压缩存储,默认策略通常已经最优。

02 /索引

只为你真的会查的路径建索引
决策树(Neon)
  1. 用什么运算符? = < > BETWEEN → B-tree;JSONB / 数组的 @> ? && → GIN;全文检索 @@ → GIN;ILIKE '%x%' → GIN + pg_trgm;范围 / 几何重叠 → GiST;追加写入、天然有序 → BRIN。
  2. 命中多少行? 超过表的 10–20% 时,索引可能还不如顺序扫描。
  3. 能缩小索引吗? 大多数查询只看某个子集 → 部分索引。
  4. 要不要免回表? 加 INCLUDE 列做覆盖索引。
  5. 列是表达式吗? 用表达式索引。
写法对照 
-- 复合索引:等值列在前,范围列在后(最左前缀)
CREATE INDEX ON orders (status, created_at);

-- 覆盖索引:SELECT 的列放 INCLUDE
CREATE INDEX ON users (email) INCLUDE (name, created_at);

-- 部分索引:只索引活跃行,更小更快
CREATE INDEX ON users (email) WHERE deleted_at IS NULL;

-- 表达式索引:查询里的表达式必须一致
CREATE UNIQUE INDEX ON users (LOWER(email));

-- BRIN:超大时序表,体积极小
CREATE INDEX ON events USING brin (created_at);

最左前缀

(a,b) 能服务 WHERE a=? 和 a=? AND b>?,不能服务只有 b 的查询。

别在 B-tree 上查 JSONB

B-tree 不支持 @>。用 GIN;只做包含查询时用 jsonb_path_ops 更小更快(代价是不支持 ? 键存在)。

索引不是越多越好

每个索引都拖慢写入。要定期找“从没被用过”和“重复”的索引并删掉。

找出缺失的外键索引:

SELECT conrelid::regclass AS table_name, a.attname AS fk_column
FROM pg_constraint c
JOIN pg_attribute a ON a.attrelid = c.conrelid AND a.attnum = ANY(c.conkey)
WHERE c.contype = 'f'
  AND NOT EXISTS (
    SELECT 1 FROM pg_index i
    WHERE i.indrelid = c.conrelid AND a.attnum = ANY(i.indkey)
  );

03 /大表与分区

不到必要不分区
什么时候分
  • 表超过约 1 亿行,且查询稳定地带分区键过滤。
  • 或者维护动作(清理旧数据、批量替换)是按某个键进行的。
  • 好处:查询只扫相关分区;DROP TABLE 一个旧分区是瞬间完成,而 DELETE 要几小时。
怎么分
  • RANGE:时序数据,最常见。
  • LIST:离散值,如地区、多租户。
  • HASH:没有自然键又想均匀分布。
  • 用声明式分区(或 TimescaleDB),不要用表继承。
CREATE TABLE events (
  id         BIGINT GENERATED ALWAYS AS IDENTITY,
  created_at TIMESTAMPTZ NOT NULL,
  data       JSONB
) PARTITION BY RANGE (created_at);

CREATE TABLE events_2026_11 PARTITION OF events
  FOR VALUES FROM ('2026-11-01') TO ('2026-12-01');
限制要记住:没有全局唯一约束,主键 / UNIQUE 必须包含分区键;分区父表上不能直接 CREATE INDEX CONCURRENTLY,要用 ON ONLY 建无效父索引,再逐个分区并发建索引后挂接。

04 /多租户与安全

让数据库而不是应用来守门
共享表 + tenant_id
  • 每张表带 tenant_id,并把它放进所有相关索引(与其他列组成复合索引)。
  • 只靠应用层加 WHERE 过滤,一个 bug 就可能泄露全部租户的数据。用 RLS 兜底。
ALTER TABLE orders ENABLE ROW LEVEL SECURITY;
ALTER TABLE orders FORCE ROW LEVEL SECURITY; -- 表所有者也受约束

CREATE POLICY tenant_isolation ON orders
  USING (tenant_id = current_setting('app.current_tenant')::int);
RLS 性能
  • 策略里的函数调用包一层 (SELECT …),否则每行都会调一次;大表上差 100 倍以上。
  • 策略用到的列要建索引。
-- 慢:每行调用一次
USING (auth.uid() = user_id)

-- 快:只算一次并缓存
USING ((SELECT auth.uid()) = user_id)
SECURITY DEFINER 函数

它以创建者权限运行并绕过 RLS,很有用也很危险。务必:

  • 放在不对外暴露的私有 schema;
  • SET search_path = '';
  • 函数体内显式校验调用者身份;
  • 对 PUBLIC 和不该调用的角色 REVOKE EXECUTE。
最小权限
  • 应用不要用超级用户,也不要 GRANT ALL——一次 SQL 注入就是灾难。
  • 分角色:只读 / 读写(不给 DELETE),登录角色继承它们。
  • 收回默认权限:REVOKE ALL ON SCHEMA public FROM public。

05 /按负载模式设计

先问:这张表是读多、写多还是更新多?
更新密集
  • 把频繁更新的列拆到单独的表(冷热分离),减少膨胀。
  • fillfactor = 90 为 HOT 更新留页内空间,省掉索引维护。
  • 避免更新带索引的列,否则无法 HOT。
  • 高频更新的行放进独立分区。
写入密集
  • 索引只留必须的,每个索引都会拖慢插入。
  • 用 COPY 或多行 INSERT(每批约 1000 行),不要逐行插。
  • 可重建的暂存数据用 UNLOGGED 表。
  • 批量导入:先删索引、导入、再重建。
  • 按时间 / 哈希分区分散压力。
Upsert
  • ON CONFLICT (a,b) 需要与之完全匹配的唯一索引(部分索引不行)。
  • 用 EXCLUDED.col 取待插入值;不需要更新时 DO NOTHING 更快。
  • 不要“先 SELECT 再 INSERT”,并发下会冲突。
队列 / 分页
  • 多 worker 抢任务用 FOR UPDATE SKIP LOCKED。
  • 翻页用游标(keyset),不要深 OFFSET——OFFSET 要扫过所有被跳过的行。
  • 消灭 N+1:用 = ANY($1::bigint[]) 或 JOIN 一次取完。
-- 原子地"领取并标记"一个任务
UPDATE jobs SET status = 'processing', worker_id = $1, started_at = now()
WHERE id = (
  SELECT id FROM jobs WHERE status = 'pending'
  ORDER BY created_at LIMIT 1
  FOR UPDATE SKIP LOCKED
)
RETURNING *;

-- 游标分页:多列排序时游标要包含全部排序列
SELECT * FROM products
WHERE (created_at, id) > ('2026-01-15 10:00:00', 12345)
ORDER BY created_at, id LIMIT 20;

06 /在线改表:哪些安全,哪些会锁

来自 Neon 与 wshobson
操作在线安全?说明
ADD COLUMN(可空,无默认值)安全只改元数据,瞬间完成
ADD COLUMN … DEFAULT x安全非易变默认值不重写表;易变默认值(now()、gen_random_uuid())加 NOT NULL 列会重写整张表
DROP COLUMN安全仅标记删除,不重写
SET NOT NULL小心要全表扫描校验;用下面的 CHECK 四步法
ALTER COLUMN TYPE不安全重写整表并持排他锁
ADD CONSTRAINT … NOT VALID安全不扫描存量行
VALIDATE CONSTRAINT安全读写不被阻塞
CREATE INDEX CONCURRENTLY安全不阻塞写入,但不能放进事务里
安全地加 NOT NULL 
-- 1. 加约束但不校验存量行
ALTER TABLE orders ADD CONSTRAINT orders_status_nn
  CHECK (status IS NOT NULL) NOT VALID;
-- 2. 后台校验(不阻塞读写)
ALTER TABLE orders VALIDATE CONSTRAINT orders_status_nn;
-- 3. 此时 SET NOT NULL 是瞬时的
ALTER TABLE orders ALTER COLUMN status SET NOT NULL;
-- 4. 删掉多余的 CHECK
ALTER TABLE orders DROP CONSTRAINT orders_status_nn;
写迁移的几个技巧
  • Postgres 大多数 DDL 是事务性的:BEGIN; ALTER …; ROLLBACK; 可以安全试跑。
  • ADD CONSTRAINT IF NOT EXISTS 不存在。要幂等,用 DO 块先查 pg_constraint。
  • 先删约束再删列,避免依赖报错。
  • CREATE OR REPLACE FUNCTION 参数不同时会新建重载而不是替换,需要手动 DROP 旧版本。

07 /连接、锁与诊断

性能问题大多出在这里
连接
  • 每个连接占约 1–3MB 内存;一定要用连接池(PgBouncer)。
  • 多数应用用事务模式;命名预处理语句在事务池里会找不到,改用无名语句,或用会话模式。
  • max_connections 实务上 100–200 即可;work_mem × 连接数 别超过内存的约 25%。
  • 池大小经验值:CPU 核数 × 2 + 磁盘数。
锁与事务
  • 事务要短,不要在事务里调外部 API,否则锁会被持有几秒。
  • 多行加锁按固定顺序(如按 id),避免死锁。
  • 设置超时:idle_in_transaction_session_timeout = '30s'、statement_timeout。
  • 只需应用层互斥时,用 advisory lock,不要造“锁行”。
诊断
  • EXPLAIN (ANALYZE, BUFFERS):大表 Seq Scan、Rows Removed by Filter 很大 → 缺索引;Sort Method: external merge → work_mem 偏小。
  • 启用 pg_stat_statements,按总耗时找最该优化的查询。
  • 大批量变更后 ANALYZE;热点表调低 autovacuum 的触发比例。

08 /可直接用的建表模板

综合以上规则
CREATE TABLE users (
  user_id    BIGINT GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
  email      TEXT NOT NULL,
  name       TEXT NOT NULL,
  created_at TIMESTAMPTZ NOT NULL DEFAULT now()
);
CREATE UNIQUE INDEX users_email_lower_uq ON users (LOWER(email));

CREATE TABLE orders (
  order_id   BIGINT GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
  user_id    BIGINT NOT NULL REFERENCES users(user_id),
  status     TEXT NOT NULL DEFAULT 'PENDING'
             CHECK (status IN ('PENDING','PAID','CANCELED')),
  total      NUMERIC(10,2) NOT NULL CHECK (total > 0),
  created_at TIMESTAMPTZ NOT NULL DEFAULT now()
);
CREATE INDEX orders_user_id_idx    ON orders (user_id);    -- 外键必须手动建索引
CREATE INDEX orders_created_at_idx ON orders (created_at);

CREATE TABLE profiles (
  user_id BIGINT PRIMARY KEY REFERENCES users(user_id),
  attrs   JSONB NOT NULL DEFAULT '{}' CHECK (jsonb_typeof(attrs) = 'object'),
  theme   TEXT GENERATED ALWAYS AS (attrs->>'theme') STORED
);
CREATE INDEX profiles_attrs_gin ON profiles USING GIN (attrs);

上线前自查清单

  • 每张引用表都有主键,ID 用 bigint identity(或 UUIDv7)。
  • 时间用 timestamptz,金额用 numeric,字符串用 text。
  • 该非空的列都加了 NOT NULL,有 CHECK 兜住取值范围。
  • 所有外键列都有索引,并写明了 ON DELETE 行为。
  • 索引只对应真实查询;复合索引等值列在前、范围列在后。
  • 多租户表带 tenant_id 并启用 RLS,策略里的函数用 (SELECT …) 包裹。
  • 应用使用连接池和最小权限角色,设置了语句 / 空闲事务超时。
  • 迁移已按“在线安全”表审过:没有易变默认值加 NOT NULL、没有直接改列类型。
