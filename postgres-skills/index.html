键与约束

R01 · 键与约束

外键列必须建索引

每个外键的引用列(子表一侧)都要有以它为前导的索引;PostgreSQL 不会自动创建。
适用前提 / 版本
所有版本;子表 ≥ 百万行时影响最大。读写比极端偏写、且从不删除/更新父行的表可以例外。
证据
  • 官方文档https://www.postgresql.org/docs/18/ddl-constraints.html#DDL-CONSTRAINTS-FK — 官方文档明确:引用列不会自动建索引,删除/更新父行时需要在子表中查找引用行。
  • 实验实验(PG18.6,子表 10,000,000 行):删除一个没有子行的父行,无索引中位数 607 ms,有索引 0.10 ms(6 次,无索引范围 578 ms–674 ms)。
后果与代价
索引 86.1 MB,建索引 3.5 秒;批量写入子表 20 万行的中位数 1,453 ms → 2,186 ms(每个索引都会增加写入成本)。
反例
子表很小(< 数万行);父表是只增不删的字典表;已有以外键列开头的复合索引时无需另建(检查查询已考虑这一点)。
检查查询

外键列没有以它为前导的索引

展开 SQL
SELECT c.conrelid::regclass AS table_name, c.conname AS foreign_key
FROM pg_constraint c
WHERE c.contype = 'f'
  AND NOT EXISTS (
    SELECT 1 FROM pg_index i
    WHERE i.indrelid = c.conrelid
      AND (string_to_array(i.indkey::text, ' ')::int2[])[1:array_length(c.conkey, 1)] = c.conkey)
示例 SQL
展开(已在 PG18.6 上实际执行通过)
CREATE TABLE r01_parent (id bigint GENERATED ALWAYS AS IDENTITY PRIMARY KEY);
CREATE TABLE r01_child (
  id bigint GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
  parent_id bigint NOT NULL REFERENCES r01_parent (id)
);
CREATE INDEX ON r01_child (parent_id);
来源分歧与裁决
四个 Skill 都认同,无分歧。倍率(约 6,072 倍)受缓存与硬件影响很大,此处只证明量级,不要当作固定值。
R05 · 键与约束

自增主键用 identity,不用 serial

用 GENERATED ALWAYS AS IDENTITY(或 BY DEFAULT);不要用 serial / bigserial。
适用前提 / 版本
PostgreSQL 10+。
证据
  • 官方文档https://wiki.postgresql.org/wiki/Don't_Do_This — 官方 wiki 推荐用 identity 代替 serial(序列归属与权限更清晰)。
  • 实验实验:只授予 INSERT 权限的角色——serial 表: permission denied for sequence t_serial_id_seq;identity 表:OK。显式指定 id:serial OK(允许手工指定 id);identity(ALWAYS)被拒绝(防止手工值与序列冲突)。
后果与代价
迁移旧表时需要把 serial 转换为 identity(需要排他锁,计划维护窗口)。
反例
BY DEFAULT 允许手工指定 id,适用于数据导入场景。
检查查询

仍在使用 serial(默认值为 nextval 的非 identity 列)

展开 SQL
SELECT a.attrelid::regclass AS table_name, a.attname AS column_name, pg_get_expr(d.adbin, d.adrelid) AS default_expr
FROM pg_attribute a JOIN pg_class cl ON cl.oid = a.attrelid JOIN pg_namespace n ON n.oid = cl.relnamespace
JOIN pg_attrdef d ON d.adrelid = a.attrelid AND d.adnum = a.attnum
WHERE a.attnum > 0 AND NOT a.attisdropped AND 
  cl.relkind IN ('r','p') AND n.nspname NOT IN ('pg_catalog','information_schema','pg_toast')

  AND a.attidentity = '' AND pg_get_expr(d.adbin, d.adrelid) LIKE 'nextval(%'
示例 SQL
展开(已在 PG18.6 上实际执行通过)
CREATE TABLE r05_items (
  id bigint GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
  name text NOT NULL
);
来源分歧与裁决
wshobson 推荐 identity,neon 明确写 “Avoid serial / bigserial”,与官方 wiki 和实验一致,无分歧。
R06 · 键与约束

大表主键:bigint identity 或 UUIDv7,避免随机 UUIDv4

亿级写入表默认 bigint identity;需要分布式生成/不可猜测 ID 时用 uuidv7();避免用 uuidv4 / gen_random_uuid() 作主键。
适用前提 / 版本
PostgreSQL 18(原生 uuidv7());数据量大于 shared_buffers 时差距最明显。本次实验 shared_buffers=256MB,表索引总量远大于它。
证据
  • 官方文档https://www.postgresql.org/docs/18/datatype-uuid.html — PG18 文档:新增 uuidv7(),按时间有序生成;uuidv4() 为随机。
  • 实验实验(PG18.6,5,000,000 行插入,3 轮中位数):插入耗时 bigint 6.5s / uuidv7 11.3s / uuidv4 23.8s(uuidv4 = uuidv7 的 2.1 倍);WAL 752 MB / 819 MB / 891 MB;主键索引 107 MB / 150 MB / 195 MB(uuidv4 比 uuidv7 大 30%);磁盘读块数 55 / 24 / 1073。
后果与代价
uuid 是 16 字节,即便是 v7 也比 bigint 慢:本实验 uuidv7 比 bigint 慢 1.7 倍,索引大 40%(含 uuidv7() 的生成开销)。
反例
外部可见的 ID 需要不可猜测时,uuidv7 的时间前缀会泄露创建时间(它本身并不是密钥)。表小于内存时 v4 的惩罚不明显。
检查查询

主键是 uuid 且默认值为随机 UUID(v4)

展开 SQL
SELECT a.attrelid::regclass AS table_name, a.attname AS column_name, pg_get_expr(d.adbin, d.adrelid) AS default_expr
FROM pg_index i
JOIN pg_attribute a ON a.attrelid = i.indrelid AND a.attnum = ANY (i.indkey)
JOIN pg_class cl ON cl.oid = a.attrelid JOIN pg_namespace n ON n.oid = cl.relnamespace
JOIN pg_attrdef d ON d.adrelid = a.attrelid AND d.adnum = a.attnum
WHERE i.indisprimary AND a.atttypid = 'uuid'::regtype AND 
  cl.relkind IN ('r','p') AND n.nspname NOT IN ('pg_catalog','information_schema','pg_toast')

  AND pg_get_expr(d.adbin, d.adrelid) ~ '(gen_random_uuid|uuidv4|uuid_generate_v4)'
示例 SQL
展开(已在 PG18.6 上实际执行通过)
CREATE TABLE r06_events (
  id uuid PRIMARY KEY DEFAULT uuidv7(),
  payload text
);
SELECT uuidv7() < uuidv7() AS ordered;
来源分歧与裁决
supabase 与 neon 明确反对 UUIDv4 主键;wshobson 允许 gen_random_uuid() 作为备选。实测支持前者(耗时 2 倍以上)。
R15 · 键与约束

UNIQUE 与 NULL;ON CONFLICT 必须匹配索引

可空列上的唯一约束默认允许多个 NULL,需要“最多一个 NULL”时用 NULLS NOT DISTINCT(PG15+);ON CONFLICT 的目标要和唯一索引(含 WHERE 谓词)一致。
适用前提 / 版本
PostgreSQL 15+。
证据
  • 官方文档https://www.postgresql.org/docs/18/ddl-constraints.html#DDL-CONSTRAINTS-UNIQUE-CONSTRAINTS — 官方文档:唯一约束中 NULL 互不相等,可用 NULLS NOT DISTINCT 改变。
  • 官方文档https://www.postgresql.org/docs/18/sql-insert.html — 官方文档:ON CONFLICT 支持 index_predicate,用于推断部分唯一索引。
  • 实验实验:默认唯一约束 第二个 NULL:允许;NULLS NOT DISTINCT 第二个 NULL:拒绝。部分唯一索引 + ON CONFLICT:不写谓词 → 报错 “no unique or exclusion constraint matching”;带谓词 → OK。
后果与代价
NULLS NOT DISTINCT 只有 PG15+;部分唯一索引的 ON CONFLICT 必须重复写谓词。
反例
业务上确实允许多个 NULL 的列(如可选的唯一编号)。
检查查询

唯一索引涉及可空列但允许多个 NULL(未使用 NULLS NOT DISTINCT)

展开 SQL
SELECT i.indexrelid::regclass AS index_name, i.indrelid::regclass AS table_name
FROM pg_index i JOIN pg_class tc ON tc.oid = i.indrelid JOIN pg_namespace n ON n.oid = tc.relnamespace
WHERE i.indisunique AND NOT i.indisprimary AND NOT i.indnullsnotdistinct AND 
  tc.relkind IN ('r','p') AND n.nspname NOT IN ('pg_catalog','information_schema','pg_toast')

  AND EXISTS (SELECT 1 FROM pg_attribute a WHERE a.attrelid = i.indrelid
              AND a.attnum = ANY ((string_to_array(i.indkey::text, ' ')::int2[])[1:i.indnkeyatts])
              AND NOT a.attnotnull)
示例 SQL
展开(已在 PG18.6 上实际执行通过)
CREATE TABLE r15_users (id bigint GENERATED ALWAYS AS IDENTITY PRIMARY KEY, email text, deleted_at timestamptz);
CREATE UNIQUE INDEX r15_email_live ON r15_users (email) WHERE deleted_at IS NULL;
INSERT INTO r15_users (email) VALUES ('a@x.com')
ON CONFLICT (email) WHERE deleted_at IS NULL DO NOTHING;
CREATE TABLE r15_nnd (a int UNIQUE NULLS NOT DISTINCT);
来源分歧与裁决
wshobson 的 details.md 写 “partial indexes don't work” with ON CONFLICT。实测:不带谓词确实报错,带 WHERE 谓词可以工作。这是 Skill 与官方文档/实验的分歧,裁决:以实验为准——Skill 的说法对一半。

数据类型

R02 · 数据类型

时间点用 timestamptz,不用 timestamp

表示“某个时刻”的列一律用 timestamptz;不要给 timestamptz 指定精度;避免 timetz。
适用前提 / 版本
所有版本、所有负载。timestamp 仅适用于“墙上时钟时间、与时区无关”的业务值(如固定的营业时间)。
证据
  • 官方文档https://wiki.postgresql.org/wiki/Don't_Do_This — 官方 wiki《Don't Do This》:不要用 timestamp(无时区)来表示时刻。
  • 官方文档https://www.postgresql.org/docs/18/datatype-datetime.html — 官方文档:timestamptz 以 UTC 存储,按会话时区显示。
  • 实验实验:同一个字面量 2026-03-08 12:00:00+09 (东京中午12点) 写入两种列。会话为 UTC 时 timestamp 列读出 2026-03-08 12:00:00,timestamptz 读出 2026-03-08 03:00:00+00;会话为东京时两者读出相同——timestamp 列丢掉了时区信息,结果随会话变化的是 timestamptz 的显示而非时刻本身。纽约夏令时切换日:+1 day = 2026-03-08 12:00:00-04,+24 hours = 2026-03-08 13:00:00-04。
后果与代价
无额外存储成本(两者都是 8 字节)。需要在应用层明确会话时区。
反例
只表示“日历日期/每日固定营业时间”的列可以用 date / time / timestamp。
检查查询

使用了 timestamp / timetz,或给 timestamptz 指定了精度

展开 SQL
SELECT a.attrelid::regclass AS table_name, a.attname AS column_name, format_type(a.atttypid, a.atttypmod) AS type
FROM pg_attribute a JOIN pg_class cl ON cl.oid = a.attrelid JOIN pg_namespace n ON n.oid = cl.relnamespace
WHERE a.attnum > 0 AND NOT a.attisdropped AND 
  cl.relkind IN ('r','p') AND n.nspname NOT IN ('pg_catalog','information_schema','pg_toast')

  AND (a.atttypid IN ('timestamp'::regtype, 'timetz'::regtype)
       OR (a.atttypid = 'timestamptz'::regtype AND a.atttypmod <> -1))
示例 SQL
展开(已在 PG18.6 上实际执行通过)
CREATE TABLE r02_events (
  id bigint GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
  happened_at timestamptz NOT NULL DEFAULT now()
);
来源分歧与裁决
无分歧。预测命中(语义演示)。
R03 · 数据类型

字符串用 text(需要限长时加 CHECK),避免 char(n)

默认用 text;确需限长时用 CHECK (length(col) <= n) 而不是 varchar(n);不要用 char(n)。
适用前提 / 版本
所有版本。若你的驱动/ORM 需要 varchar(n) 元数据,可保留 varchar(n),性能没有差别。
证据
  • 官方文档https://www.postgresql.org/docs/18/datatype-character.html — 官方文档:text、varchar(n)、char(n) 在 PostgreSQL 中存储方式相同,char(n) 额外补空格,没有性能优势。
  • 实验实验(3,000,000 行,点查 pgbench 5 轮):text 中位 14,318 TPS(范围 14,143–14,749),varchar(32) 13,778(范围 13,676–14,412);两者表/索引体积完全相同(175 MB / 118 MB)。char(32):表 219 MB(+25%),索引 169 MB(+43%)。
  • 实验意外发现(预测没有想到):char(n) 列与 text 表达式比较(例如 col = md5(...))会被转成 ::text,无法使用 char(n) 上的索引,退化为顺序扫描——下面的 EXPLAIN 在 PG18 上实测。
后果与代价
改限长时 CHECK 约束可以 NOT VALID 在线添加;varchar(n) 缩小长度的重写行为属文档层面说法,本手册未验证。
反例
与遗留系统/外部 schema 对接且要求 char(n) 的场景。
检查查询

使用了 char(n) / varchar(n)

展开 SQL
SELECT a.attrelid::regclass AS table_name, a.attname AS column_name, format_type(a.atttypid, a.atttypmod) AS type
FROM pg_attribute a JOIN pg_class cl ON cl.oid = a.attrelid JOIN pg_namespace n ON n.oid = cl.relnamespace
WHERE a.attnum > 0 AND NOT a.attisdropped AND 
  cl.relkind IN ('r','p') AND n.nspname NOT IN ('pg_catalog','information_schema','pg_toast')

  AND a.atttypid IN ('bpchar'::regtype, 'varchar'::regtype) AND a.atttypmod <> -1
示例 SQL
展开(已在 PG18.6 上实际执行通过)
CREATE TABLE r03_users (
  id bigint GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
  email text NOT NULL CHECK (length(email) <= 254)
);
-- char(n) 与 text 比较:不能走索引(Seq Scan),显式转换为 char(n) 才行
CREATE TABLE r03_c (code char(32) PRIMARY KEY);
INSERT INTO r03_c SELECT md5(g::text) FROM generate_series(1, 20000) g;
ANALYZE r03_c;
EXPLAIN SELECT 1 FROM r03_c WHERE code = md5('5');
EXPLAIN SELECT 1 FROM r03_c WHERE code = md5('5')::char(32);
来源分歧与裁决
supabase / wshobson / neon / ECC 一致主张 text。官方文档同样认为 varchar(n) 无性能收益——但这一点实测只在“相同长度语义”下成立,见上面 char(n) 的索引陷阱。
R04 · 数据类型

金额用 numeric,不用 float / money

金额、费率等需要精确十进制的列用 numeric(p,s);不要用 real / double precision;不要用 money。
适用前提 / 版本
所有版本。科学计算、传感器等本身有测量误差的数据可以用 float8。
证据
  • 官方文档https://wiki.postgresql.org/wiki/Don't_Do_This — 官方 wiki:不要用 money;浮点数不适合存储精确金额。
  • 实验实验:100 万个 0.1 求和,float8 = 100000.00000133288,numeric = 100000.0;0.1+0.2=0.3 在 float8 为 False,numeric 为 True。
后果与代价
numeric 比 float8 占更多空间、运算更慢(本手册未测量,属于文档层面的常识,标为“未验证”)。
反例
聚合分析、机器学习特征等不要求精确十进制语义的列。
检查查询

金额类列使用了 money 或浮点数

展开 SQL
SELECT a.attrelid::regclass AS table_name, a.attname AS column_name, format_type(a.atttypid, a.atttypmod) AS type
FROM pg_attribute a JOIN pg_class cl ON cl.oid = a.attrelid JOIN pg_namespace n ON n.oid = cl.relnamespace
WHERE a.attnum > 0 AND NOT a.attisdropped AND 
  cl.relkind IN ('r','p') AND n.nspname NOT IN ('pg_catalog','information_schema','pg_toast')

  AND (a.atttypid = 'money'::regtype
       OR (a.atttypid IN ('float4'::regtype, 'float8'::regtype)
           AND a.attname ~* '(price|amount|total|balance|cost|fee|salary|money)'))
示例 SQL
展开(已在 PG18.6 上实际执行通过)
CREATE TABLE r04_payments (
  id bigint GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
  amount numeric(12,2) NOT NULL CHECK (amount >= 0)
);
SELECT sum(0.1::float8) AS float_sum, sum(0.1::numeric) AS numeric_sum FROM generate_series(1, 1000000);
来源分歧与裁决
无分歧。

索引

R07 · 索引

复合索引:等值列在前、范围列在后——但 PG18 不再是绝对的“最左前缀”

多列索引默认把等值条件的列放前面、范围/排序列放后面;PG18 起,前导列取值很少(几十个以内)时,缺失前导列的查询也能借助 skip scan 使用该索引。
适用前提 / 版本
PostgreSQL 18。PG17 及以前按旧的最左前缀行为。前导列取值很多时 skip scan 无益。
证据
  • 官方文档https://www.postgresql.org/docs/18/release-18.html — PG18 Release Notes:B-tree 多列索引支持 skip scan。
  • 官方文档https://www.postgresql.org/docs/18/indexes-multicolumn.html — 官方文档:多列索引的前导列条件对效率影响最大。
  • 实验实验(10,000,000 行;status 5 个取值,customer_id 约 90 万个取值):索引 (status, created_at),只按时间范围查询(缺 status):PG18 1.62 ms、90 个缓冲区、11 次索引搜索;PG16 217 ms、38493 个缓冲区。缓冲区减少 428 倍(时间差受两个版本构建不同影响,以缓冲区为准)。
  • 实验前导列取值多时无效:索引 (customer_id, created_at),只按时间查询,PG18 仍需 38,318 个缓冲区,与 PG16 的 38,318 相同。
后果与代价
索引体积约 302 MB;把范围列放前面 (created_at, status) 对“等值+范围”查询略慢(0.45 ms vs 0.12 ms)。
反例
skip scan 的搜索次数 ≈ 前导列的取值个数;取值个数多时反而不如重新设计索引。
检查查询

多列 B-tree 索引的前导列只有少量取值(≤200),需复核列顺序;PG18 起此类索引可被 skip scan 利用

展开 SQL
SELECT i.indexrelid::regclass AS index_name, i.indrelid::regclass AS table_name, a.attname AS leading_column, s.n_distinct
FROM pg_index i
JOIN pg_class ic ON ic.oid = i.indexrelid
JOIN pg_am am ON am.oid = ic.relam AND am.amname = 'btree'
JOIN pg_class tc ON tc.oid = i.indrelid
JOIN pg_namespace n ON n.oid = tc.relnamespace
JOIN pg_attribute a ON a.attrelid = i.indrelid AND a.attnum = i.indkey[0]
JOIN pg_stats s ON s.schemaname = n.nspname AND s.tablename = tc.relname AND s.attname = a.attname
WHERE n.nspname NOT IN ('pg_catalog','information_schema','pg_toast') AND i.indnkeyatts > 1 AND s.n_distinct BETWEEN 1 AND 200
示例 SQL
展开(已在 PG18.6 上实际执行通过)
CREATE TABLE r07_orders (id bigint GENERATED ALWAYS AS IDENTITY PRIMARY KEY, status text NOT NULL, created_at timestamptz NOT NULL);
INSERT INTO r07_orders (status, created_at)
SELECT (ARRAY['new','paid','shipped','done','cancelled'])[1 + g % 5], now() - (g || ' seconds')::interval
FROM generate_series(1, 200000) g;
CREATE INDEX r07_idx ON r07_orders (status, created_at);
ANALYZE r07_orders;
EXPLAIN (ANALYZE, BUFFERS, COSTS OFF, TIMING OFF)
SELECT count(*) FROM r07_orders WHERE created_at > now() - interval '1 hour';
来源分歧与裁决
supabase / wshobson / neon 都写“最左前缀,缺前导列则索引不可用”(supabase query-composite-indexes.md 注释:“Does NOT work for: WHERE created_at > …”)。在 PG18 上这条已被官方特性修正:前导列取值少时可用。裁决:以 PG18 文档 + 实验为准,但仅对低基数前导列成立。
R08 · 索引

只查少数状态的大表,用部分索引

当查询总是命中表中占比很小的一部分(如 status='pending'),用 CREATE INDEX … WHERE … 只索引这部分。
适用前提 / 版本
任意版本。分布倾斜明显(目标值占比 < 约 1%)时收益最大。
证据
  • 官方文档https://www.postgresql.org/docs/18/indexes-partial.html — 官方文档:部分索引缩小索引体积、减少维护成本;查询条件必须蕴含索引谓词。
  • 实验实验(10,000,000 行,pending 占 0.4%):部分索引 909,312 字节 vs 全量复合索引 302 MB(体积 0.29%);取最早 50 条 pending:0.02 ms vs 0.04 ms;批量写入 30 万行中位数 484 ms vs 920 ms(无索引基线 538 ms)。
后果与代价
查询必须携带与索引谓词一致的条件(绑定参数写法可能无法证明蕴含,需要用 EXPLAIN 确认)。
反例
目标值占比较高(> 10%)时部分索引收益有限。
检查查询

在分布高度倾斜的列上建了全量索引,可考虑部分索引

展开 SQL

FROM pg_index i
JOIN pg_class tc ON tc.oid = i.indrelid JOIN pg_namespace n ON n.oid = tc.relnamespace

R09 · 索引

覆盖索引(INCLUDE)要配合 VACUUM,否则不省回表

想用 Index Only Scan 时,用 INCLUDE 放入被查询的非键列,并确保 autovacuum 能及时更新可见性图。
适用前提 / 版本
任意版本。更新频繁的表需要调低 autovacuum 阈值。
证据
  • 官方文档https://www.postgresql.org/docs/18/indexes-index-only-scans.html — 官方文档:Index Only Scan 只有在页面被标记为全可见时才能省去回表。
  • 实验实验(3,000,000 行):普通索引 4.42 ms;覆盖索引 VACUUM 后 1.18 ms(Heap Fetches 0);大量 UPDATE 后、VACUUM 前 4.74 ms(Heap Fetches 6,617),基本退回到普通索引水平;再次 VACUUM 后恢复 1.18 ms。
后果与代价
覆盖索引体积 90 MB,所有 INCLUDE 列都会重复存储;写入更重。
反例
表几乎只读或只追加(可见性图稳定)时收益最大;热点更新表几乎得不到收益。
检查查询

带 INCLUDE 的覆盖索引所在表,可见性图覆盖率低(Index Only Scan 会退化)

展开 SQL

R11 · 索引

Hash 索引:更小,点查略快,但不是默认选择

只做等值查询的长文本键,可以考虑 Hash 索引;需要唯一约束、范围或排序时用 B-tree。
适用前提 / 版本
PostgreSQL 10+(Hash 索引已写 WAL)。
证据
  • 官方文档https://www.postgresql.org/docs/18/indexes-types.html — 官方文档:Hash 索引只支持等值比较;不支持唯一约束。
  • 实验实验(5,000,000 行,32 字符 md5 键,pgbench 5 轮):Hash 128 MB vs B-tree 282 MB(体积 45%);点查 TPS 中位数 15,181(范围 14,656–15,555) vs 13,917(13,352–14,007)(Hash 高 9%,两者范围不重叠,但差距很小)。
后果与代价
构建更慢(8.4s vs 6.5s);不能用于 ORDER BY / 范围 / 唯一约束 / 多列。
反例
只有等值查询、键很长、内存紧张的场景。
检查查询

使用了 Hash 索引(需确认确有收益,且不需要唯一性 / 范围 / 排序)

展开 SQL

WHERE am.amname = 'hash'

supabase 写“Hash 对等值略快于 B-tree”,wshobson / ECC 未提及 Hash 索引。实验:略快(约 +9%)且体积小一半,但收益不大,所以只作为可选项,不是通用规则。

R10 · 查询

分页用游标(keyset),大偏移的 OFFSET 会线性变慢

深分页使用 WHERE (排序键) > 上一页最后一个值 ORDER BY 排序键 LIMIT n,而不是 OFFSET。
适用前提 / 版本
任意版本。偏移量小(几百行内)时 OFFSET 没问题。
证据
  • 官方文档https://www.postgresql.org/docs/18/queries-limit.html — 官方文档:使用 OFFSET 时,被跳过的行仍然要被计算出来。
  • 实验实验(10,000,000 行,按主键排序取 20 行,5 次):OFFSET 0 / 10,000 / 100,000 / 1,000,000 / 5,000,000 → 0.01 ms / 1.27 ms / 13 ms / 137 ms / 1,011 ms;keyset 在同样位置恒为 0.01 ms–0.02 ms。
后果与代价
keyset 不能随机跳页,排序键必须唯一(或加主键作为次级键);需要前端配合。
反例
后台管理、小数据量列表;需要总页数/跳页的场景。
检查查询

pg_stat_statements 中平均耗时 > 10ms 且使用了 OFFSET 的查询(需先启用 pg_stat_statements)

展开 SQL
SELECT round(mean_exec_time::numeric, 1) AS mean_ms, calls, left(query, 100) AS query
FROM pg_stat_statements
WHERE dbid = (SELECT oid FROM pg_database WHERE datname = current_database())
  AND query ~* '\moffset\M' AND mean_exec_time > 10 AND query !~* 'pg_stat_statements'
ORDER BY mean_exec_time DESC
示例 SQL
展开(已在 PG18.6 上实际执行通过)
CREATE TABLE r10_posts (id bigint GENERATED ALWAYS AS IDENTITY PRIMARY KEY, title text NOT NULL);
INSERT INTO r10_posts (title) SELECT 'p' || g FROM generate_series(1, 1000) g;
-- 第一页
SELECT id, title FROM r10_posts ORDER BY id LIMIT 20;
-- 下一页:用上一页最后的 id
SELECT id, title FROM r10_posts WHERE id > 20 ORDER BY id LIMIT 20;
来源分歧与裁决
supabase 有专门的游标分页条目(data-pagination.md)。其余 Skill 未逐文核对,无已知分歧。

R12 · 在线迁移

大表在线加 NOT NULL:先 NOT VALID,再 VALIDATE

PG18:ADD CONSTRAINT … NOT NULL col NOT VALID → VALIDATE CONSTRAINT;PG17 及以前:CHECK (col IS NOT NULL) NOT VALID → VALIDATE → SET NOT NULL → DROP CHECK。
适用前提 / 版本
大表(扫描时间超过你能容忍的写入停顿)。PG18 原生语法需要 18+。
证据
  • 官方文档https://www.postgresql.org/docs/18/sql-altertable.html — 官方文档:SET NOT NULL 需要全表扫描;VALIDATE CONSTRAINT 只需要 SHARE UPDATE EXCLUSIVE 锁。
  • 实验实验(PG18.6,10,000,000 行,并发写入 + 读取探针,pg_locks 轮询):直接 SET NOT NULL 耗时 1,076 ms,持有 AccessExclusiveLock,写入探针最长停顿 1,075 ms,读取探针最长停顿 1,076 ms。CHECK 四步法:VALIDATE 耗时 945 ms,只持有 ShareUpdateExclusiveLock,最长停顿写 5.50 ms / 读 4.50 ms;PG18 原生:VALIDATE 1,213 ms,写 4.40 ms / 读 6.60 ms。
后果与代价
本实验数据全部在内存缓存中,10,000,000 行的直接做法只停顿约 1 秒——停顿与表大小、IO 速度成正比,冷数据/亿级表会按比例放大(未在本环境验证亿级)。
反例
表很小或可停机时,直接 SET NOT NULL 更简单。锁排队:任何需要 ACCESS EXCLUSIVE 的 DDL 前都应设置 lock_timeout。
检查查询

可空但统计显示从无 NULL 的列,可评估补上 NOT NULL(用 NOT VALID 在线添加)

展开 SQL
SELECT a.attrelid::regclass AS table_name, a.attname AS column_name, s.null_frac
FROM pg_attribute a JOIN pg_class cl ON cl.oid = a.attrelid JOIN pg_namespace n ON n.oid = cl.relnamespace
JOIN pg_stats s ON s.schemaname = n.nspname AND s.tablename = cl.relname AND s.attname = a.attname
WHERE a.attnum > 0 AND NOT a.attisdropped AND NOT a.attnotnull AND 
  cl.relkind IN ('r','p') AND n.nspname NOT IN ('pg_catalog','information_schema','pg_toast')

  AND s.null_frac = 0 AND cl.reltuples > 0
示例 SQL
展开(已在 PG18.6 上实际执行通过)

INSERT INTO r12_t (note) SELECT 'x' FROM generate_series(1, 1000);

来源分歧与裁决
wshobson / neon 提到 NOT VALID(针对 CHECK / 外键);PG18 原生 NOT NULL NOT VALID 在它们的文本中没有出现——属于新版本特性带来的更新。
R13 · 在线迁移

大表加列:只用常量/稳定默认值,不用易变默认值

ADD COLUMN … DEFAULT 常量(或 STABLE 函数如 now())是瞬时的;DEFAULT 易变函数(clock_timestamp()、gen_random_uuid()、uuidv7())会重写整表。
适用前提 / 版本
PostgreSQL 11+。
证据
  • 官方文档https://www.postgresql.org/docs/18/sql-altertable.html — 官方文档:默认值非易变时无需重写表;易变默认值会重写。
  • 实验实验(PG18.6,10,000,000 行):DEFAULT 0 8.20 ms,relfilenode 未变;DEFAULT clock_timestamp() 11,335 ms(重写,写入探针最长停顿 10,593 ms);DEFAULT uuidv7() 21,693 ms(重写,停顿 20,918 ms)。
  • 实验额外验证(1,000,000 行小表,relfilenode 对比):DEFAULT now() 不重写;DEFAULT gen_random_uuid() 重写——now() 是 STABLE 而非 VOLATILE。
后果与代价
易变默认值需要分批回填:先加可空列,再分批 UPDATE,最后加约束。
反例
可以接受停机的小表。
检查查询

(无法用目录查询检查)迁移脚本里为大表加列时使用了易变默认值 —— 用迁移 linter(Squawk)检查迁移文件,见 README

展开 SQL

R14 · 在线迁移

线上建索引用 CREATE INDEX CONCURRENTLY,并检查无效索引

在有写入的表上建索引用 CONCURRENTLY;失败后要清理 INVALID 索引。
适用前提 / 版本
任意版本。CONCURRENTLY 不能放在事务块里。
证据
  • 官方文档https://www.postgresql.org/docs/18/sql-createindex.html — 官方文档:普通 CREATE INDEX 阻塞写入;CONCURRENTLY 持 SHARE UPDATE EXCLUSIVE,失败会留下无效索引。
  • 实验实验(10000000 行,并发写/读探针):普通建索引 4,521 ms,持有 ShareLock,写入最长停顿 4,521 ms;CONCURRENTLY 6,450 ms(为普通方式的 1.43 倍),持有 ShareUpdateExclusiveLock,写入最长停顿 8.60 ms。
后果与代价
耗时更长(本实验 1.4 倍),需要等待旧事务结束;失败会留下 INVALID 索引占用写入成本。
反例
新建的空表/可停机窗口,普通 CREATE INDEX 更快。
检查查询

失败的 CREATE INDEX CONCURRENTLY 留下的无效索引

04 /未验证 / 待核实

诚实清单
  • 亿级表的迁移停顿:R12/R13/R14 只在 1000 万行、数据全在内存缓存的条件下测量。停顿时间应与表大小、IO 速度成正比,但本环境没有验证亿级。验证脚本:LAB_N=100000000 python3 00_build_base.py && python3 exp_migrate.py(需要数百 GB 磁盘与较长时间)。
  • 托管云环境的绝对数值:实验在 2 核 / 8GB / 本地盘 / fsync=off 的单机上跑,所有绝对耗时不能外推到你的云实例。只有相对关系(倍数、缓冲区数、字节数)有参考价值。请在自己的实例上用 lab/ 的脚本复测。
  • numeric 相对 float8 的性能代价:R04 只验证了精度,没有测量求和 / 存储开销。脚本待补。
  • PG16 与 PG18 的耗时对比:两个版本是不同的构建,耗时对比被构建差异干扰(同一查询、同一数据时 PG18 在高基数列上反而更慢 2×,但缓冲区完全相同)。因此版本差异只用缓冲区数量做结论。
  • uuidv7() 的生成开销:R06 的 uuidv7 比 bigint 慢 1.6×,其中有多少来自函数调用、多少来自索引局部性,没有拆开。
  • 来自 Skill 的经验阈值:“顺序扫描阈值 10–20%”“连接池大小公式”等出现在部分 Skill 中,本手册没有测试,因此没有收入 15 条规则。
  • 文档链接:沙箱网络只允许访问部分站点,页面里的官方文档链接没有逐个抓取核对锚点;结论来自搜索摘录与实验,请点开链接复核。
  • Skill 立场表:上面矩阵中 ✓ / ≠ 是读过原文行后的判断;○ 表示 grep 命中关键词、但没有逐文通读判断立场;— 表示没有命中。
  • 样本量:性能实验每组重复 3–6 次,给出的是中位数与范围,不是置信区间;R01 写入对比的第一轮明显偏高(4.7s),说明单次测量有噪声。
  • Squawk 覆盖:只用 3 段迁移(见 lab/migrations/)验证了 Squawk 2.72.0 能抓出 R12/R13/R14 对应的写法,不代表覆盖所有写法。

05 /如何独立复现

不需要信我
  1. 准备 PostgreSQL 18(以及对照用的 16),git clone 本仓库,进入 postgres-skills/lab。
  2. 设置环境变量:LAB_PGHOST LAB_PGPORT LAB_PGUSER(以及 LAB_N 控制行数),pip install psycopg2-binary。
  3. python3 00_build_base.py new 建基础数据,再依次运行 exp_semantics.py / exp_index.py / exp_types.py / exp_migrate.py,结果写入 results/*.json。
  4. python3 checks.py:在“故意违规”的库里每条检查必须有输出,在“按规则建”的库里必须为空(自测)。checks.sql 可直接对你的库运行。
  5. python3 validate_sql.py:把本页所有 SQL 在你的实例上执行一遍。
  6. npx squawk-cli migrations/bad.sql 与 migrations/good.sql:用迁移 linter 复核 R12–R14。
  7. python3 build_page.py:用你自己的 results 重新生成本页,看结论是否一致。
